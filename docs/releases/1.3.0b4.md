# v1.3.0 Beta 4 - Persistent capabilities and incremental discovery

This beta reduces restart work on slow Modbus links by preserving the register
support learned for each device. Live measurements and write confirmations are
always read from the device; they are never restored from this cache.

## Changes since Beta 3

- Store partial support maps atomically in Home Assistant storage, scoped to
  the configuration entry, endpoint, unit and device role.
- Validate inverter model, serial number and firmware on startup. Changed
  identity or register definitions invalidate the corresponding cache. If
  identity cannot be verified, only cached positives are reused; cached
  negatives cannot suppress discovery.
- Read device identity, PV string count and a small core telemetry set before
  entity setup. Reuse those bootstrap values in the first fetch. Later polls
  continue reading static metadata at their existing frequency.
- Poll known-supported registers normally. Discover unknown registers and
  perform one recheck pass of cached unsupported registers after each restart.
  Run at most one extra Modbus request per physical endpoint per update
  interval, rotating among plant, inverter and charger groups.
- Split rejected blocks across subsequent intervals. Repeatedly rejected
  regions fall back to individual fields, without a long synchronous probe
  loop. Transport failures retain capability state and back off discovery.
- After an illegal-address response during normal polling, isolate only the
  affected block. A timeout never marks a register unsupported.
- Preserve entity IDs, registry entries, history and user-disabled flags.
  Optional register entities wait for confirmed support. Newly supported
  entities can return without restarting the integration.
- Keep protected in-flight transactions intact during cancellation, and drain
  them before issuing replacement requests.
- Checkpoint capabilities from the first identity responses, including late
  replies received while a failed setup is being cleaned up. A subsequent
  setup creates a new hub and restores the confirmed capability progress.
- Persist the remaining split discovery jobs, completed checks and retry
  pacing. Setup retries/reloads continue the same pass; a full HA restart
  starts a new pass over cached negatives while retaining unfinished work.
- Back off discovery transport failures for 60, 120, 240 and at most 300
  seconds. A successful device response resets the backoff. Regular polling
  continues independently.
- Resume interrupted ordinary read rounds with completed blocks held only
  in memory. Late replies finish safely, and a per-device lock prevents
  replacement polls from stacking behind them. Discard a round older than
  180 seconds rather than publish its old samples.
- Invalidate every unfinished read round on the affected endpoint before
  and after a write, including a write whose caller was cancelled. EMS
  confirmation therefore still requires fresh post-write readback.
- Restore newly supported entities through HA's synchronous add-entities
  callback. Existing register-backed entities remain unavailable while their
  support is unresolved; synthetic diagnostics retain their own availability.
- Invalidate and queue all endpoint groups before rebuilding a changed
  identity. Interrupted bootstrap work retries before the next inverter poll.
- Timestamp bootstrap samples at the read attempt and include their age in
  the 180-second read-round limit. Expired samples are read again.
- Preserve the last verified capability record, including negative decisions
  and completed discovery checks, while early bootstrap checkpoints collect
  provisional positive progress before live identity validation.
- Pause all ordinary read workflows on an identity-changed endpoint before
  changing its cache identity or rebuilding register support. Drain surviving
  protected replies and keep new polls/discovery out of the rebuild.
- Save unverified discovery progress separately from the verified capability
  record, including split jobs, same-boot completed checks and retry pacing.
  Unverified negative checks remain pass bookkeeping, not restored negative
  capabilities. A new HA boot checks them again. Discard progress from a
  different verified identity or register schema.

## Checking the cache and timings

Restart Home Assistant completely after installing the beta. In the Sigenergy
integration menu, select **Download diagnostics**. Under `data.discovery`:

- `bootstrap_time`: seconds spent validating identity, restoring capabilities
  and reading core startup fields, before the first coordinator fetch.
- `devices`: cache status and age when loaded, supported/unsupported/unknown field counts,
  queued discovery jobs, request/failure counts and cumulative discovery time.
- Per device, `restored_jobs` counts discovery jobs restored from storage and
  `retry_in` gives the remaining discovery failure backoff in seconds.
- `poll_recovery` reports resumed/expired read rounds, buffered field count,
  current round age and the elapsed span of the last completed round. A
  recovered round can include readings from multiple attempts, up to the
  180-second limit; it is not an instantaneous snapshot. A new ordinary
  round reads all supported fields again, including static metadata.
- `cache_error`: cache loading/saving error class, if present. A broken cache
  falls back to discovery.

`data.coordinator.startup_fetch_time` measures the first coordinator fetch.
Add `discovery.bootstrap_time` to compare the Modbus initialization work with
Beta 3's startup fetch; this excludes platform setup and HA's overall boot time.
Normal poll duration and update failures/timeouts remain in `data.coordinator`.
The same discovery information is also included in device diagnostics.

On a fresh cache, optional fields appear gradually. After a warm restart,
known-supported fields are read immediately while negative rechecks run in
the background. A slow outstanding discovery request can still delay a poll
on the shared physical connection until its transport timeout; it is never
cancelled merely to interrupt the wire transaction.

**Home Assistant Core 2026.10.0+ and Python 3.14.2+ are required.**

## Startup timeout and recovery

The initial identity/core bootstrap and first coordinator fetch share the
180-second startup deadline. On failure, protected wire requests are drained,
capabilities/discovery progress are flushed, and Home Assistant schedules a
new setup attempt through `ConfigEntryNotReady`. Identity/topology is always
validated live. Measurement buffers are never restored into a new hub or
written to disk. A persistently offline device or mandatory reads exceeding
the startup budget can still require further setup attempts.

Runtime fetches keep the 60-second coordinator deadline. A cancelled read
round can continue in the same hub on the next update, within the memory
age limit. Capability knowledge is preserved on transport errors. Shared
connection reconnects remain managed by HA's Modbus broker.

## Local verification

On 2026-10-17, a local HA 2026.10.1 installation restored all three device
support maps after a complete restart. Identity/cache bootstrap took 0.059 s
and the first fetch 0.197 s: **0.256 s of Modbus initialization**, compared
with the same installation's recorded Beta 3 startup fetch of 2.325 s.
Subsequent sampled polls took 0.121-0.170 s, with zero recorded update
failures or timeouts. All 176 plant and 145 inverter fields previously
returning data still returned live values. All 398 entity IDs, device links
and disabled flags were preserved.

An integration reload completed in 0.625 s and restored 92 pending discovery
jobs. The discovery pass, prior completed checks, interval pacing and all
unfinished work were retained or completed. Optional negative rechecks
continued in the background. There were no Sigenergy component warnings or
errors. Two dependent HA template sensors logged errors during the brief
sensor unavailability around reload.

All 156 local regression tests passed on Python 3.12 with both
`modbus-connection==4.12.3` and `4.12.4`, including persistence, identity/schema
invalidation, first-identity and first-fetch setup deadlines followed by a new
hub, persisted split jobs/backoff, runtime deadline continuation, expired
sample rejection, interval limits across reload, write invalidation, entity
restoration and existing EMS readback coverage. Runtime checks used the HA
API; this installation does not expose Sigenergy entities through its MCP
live-context tool.

The PR review fixes add coverage for synchronous entity callbacks, implicit
register availability, interrupted identity rebuilds, bootstrap sample expiry,
and preservation of verified cache decisions across an early failed setup.
The live measurements above precede these review fixes.
Further coverage exercises sibling polls spanning multiple wire requests,
cancelled polls/rebuilds, exclusion of new polls and discovery during rebuild,
reloads with incomplete identity, new-boot negative rechecks, and interrupted
changed-identity setup without carrying over old completed checks.
