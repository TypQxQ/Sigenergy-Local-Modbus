# v1.3.0 Beta 6 - Explain PV energy restoration

Following the restart results and suggestions in issue #436, this beta makes PV
counter restoration visible without enabling verbose power-integration logging.

## Changes since Beta 5

- Log each successful PV counter restoration at INFO, once per entity setup.
  Include the source, exact native value in kWh, sample timestamp, attempt count,
  current attempt duration and total elapsed time including retry delays.
  Explicit manual initialization is identified separately as `manual_config`.
- Measure Recorder executor queue wait separately from the history query time.
  A retry reuses the original job and its timing measurements. A pending-job
  timeout reports elapsed time and pending status; it cannot yet establish
  whether that job is queued or reading the database.
- Add independent DEBUG logging under `custom_components.sigen.pv_restore` for
  normalized candidates and selection reasons: newest timestamp, native snapshot
  precision on a tie, missing/invalid data, a post-start timestamp, a genuinely new
  counter or a previous local day. Recorder fallback reads and query errors also
  have diagnostic context.
- Normal power updates do not emit restoration INFO logs or add Recorder reads.

The 10-second initial wait, 60-second retry, counter selection, unit conversion,
midnight behavior and Modbus polling remain unchanged. Existing counters with
unverified restoration data continue to stay unknown rather than starting at
zero. Historical energy statistics are not modified.

## Reading the logs

INFO reports native **kWh**, even when Home Assistant displays that entity in
MWh. `sample_updated` dates the chosen saved value, while `total_elapsed` measures
time since the first restoration attempt, including retry delays. Queue and query
times describe the actual Recorder job, not an unrelated integration's setup.

For detailed selection decisions, enable only the restore helper's DEBUG category:

```yaml
logger:
  logs:
    custom_components.sigen.calculated_sensor: info
    custom_components.sigen.pv_restore: debug
```

This keeps the per-power-change DEBUG output in `calculated_sensor` disabled.
Merge these logger entries into an existing logger configuration if needed.

Restart Home Assistant completely after installing Beta 6 to load the updated
Python modules. An integration reload alone does not reload their code.

## Verification

- All 211 regression tests passed on Python 3.14.7 with both
  `modbus-connection==4.12.3` and `4.12.4`.
- Regression coverage includes INFO source/value/timestamp reporting, separate
  queue/query timing, DEBUG selection decisions, query failures and the
  timeout/retry path retaining one executor job and the original elapsed time.
- The existing PV restore, native unit/precision, midnight/DST, manual-reset,
  unknown-on-failure, entity lifecycle and polling tests remain in the suite.
- A full restart of the dev installation on Home Assistant 2026.10.2 loaded B6
  and produced exactly one successful INFO restoration per PV counter, six in
  total, plus the independent DEBUG selection/query details. All six PV energy
  values were unchanged, 27 numeric energy sensors retained their units and
  cumulative values, and all 398 registry identities/device links/user-disabled
  flags were preserved. No update failures or timeouts were recorded; sampled
  polls were around 0.2 seconds. This live check ran after solar production had
  stopped; the timeout/retry and stale-snapshot paths are covered by regression
  tests rather than a forced live database failure.

**Home Assistant Core 2026.10.0+ and Python 3.14.2+ are required.**
