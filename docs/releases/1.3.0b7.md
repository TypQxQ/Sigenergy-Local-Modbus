# v1.3.0 Beta 7 - Faster PV recovery and partial-read diagnostics

## Changes since Beta 6

- When a PV counter's Recorder query exceeds the initial 10-second wait, use
  its completion to resume restoration immediately. The 60-second retry remains
  a watchdog and the backoff for failed queries or unverified data. Reuse the
  existing query; timer and completion cannot start duplicate restore tasks.
  Removal cancels recovery, and pending daily counters still respect midnight.
- Include PV restore status in both integration and device diagnostics, under
  `pv_restore`, without extra Recorder queries or changes to logger settings.
  Each counter reports status, selected source, exact restored native kWh value
  as a string, sample timestamp, attempts, elapsed time, Recorder queue/query
  time and latest error type/stage. Pending ages are calculated at download time.
  The restored value describes the startup baseline, not the current live total.
  Entity removal clears its entry; reloads cannot erase a newer entity's status.
- Count completed polls with failed supported-register reads or decoder failures
  as `partial`, with a separate `partial_update_count` for the coordinator and
  device group. Per-device diagnostics retain affected fields, block addresses,
  register space, error type, last failure and recovery timestamp. Interrupted
  read rounds keep late block failures through their normal polling recovery.
- Keep healthy values available during partial reads. Existing whole-update
  failure/timeout counters retain their meaning. Unknown or confirmed unsupported
  registers and background discovery do not count as failed supported reads.
  A successful read status refers to attempted supported registers; capability
  discovery can still be incomplete. Downloaded diagnostics retain the last
  failure after active read errors clear.
- Log one WARNING when a device enters a degraded state and one INFO when its
  supported reads recover. Repeated degraded polls update diagnostics without
  repeating the warning. Diagnostics include error types, not raw error text or
  register payloads.
- Correct the DEBUG explanation for equal-timestamp restore samples to
  `snapshot preferred at equal timestamp`. Missing or invalid native restore
  data can use a stored display state, so a tie does not always imply native
  precision.

Counter selection, native precision, unit conversion, polling intervals and
static metadata reads are unchanged. Existing counters with unverified restore
data remain unknown instead of starting at zero. Historical energy statistics
are not modified.

## Reading diagnostics

The coordinator section reports `partial_update_count` and
`latest_update_timing.status`. The latter can be `success`, `partial`, `error`,
`timeout` or `cancelled`. Device timing entries include their read quality.
Under `discovery.devices`, each group's `poll_quality` holds its current and
most recent failed-read details. These runtime counters reset on reload/restart.

`pv_restore` is keyed by entity ID. Status progresses through `pending`,
`reading`, `waiting_for_recorder` or `retry_scheduled`, then `restored`.
The last error remains available after recovery, distinguished by the restored
status. Manual counter initialization is identified as `manual_config`.

## Verification

All 230 regression tests passed locally on Python 3.14.7 with both
`modbus-connection==4.12.3` and `4.12.4`.

Regression coverage includes immediate completion after timeout, timer/completion
races, late query failures and cancellation, entity removal/reload, native
precision, midnight/DST behavior, partial block reads, decoder failures,
capability discovery, resumed reads and both diagnostic download entry points.

Restart Home Assistant completely after installing Beta 7 to load the updated
Python modules. An integration reload alone does not reload their code.

**Home Assistant Core 2026.10.0+ and Python 3.14.2+ are required.**
